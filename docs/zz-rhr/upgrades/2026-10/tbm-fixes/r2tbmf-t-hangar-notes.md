## Existing native ownership

- `Order` already saves `OT_GOTO_DEPOT` with a genuine16-bit `DepotID`, ordinary Service/Halt flags and native shared-order semantics. `CmdInsertOrder` validates the depot pool object and tile type. `Order::GetLocation` resolves that object's actual `xy`; no TileIndex can be cast to a destination ID.
- `Depot` owns its actual tile, naming and lifecycle. Its destructor removes ordinary depot orders and backups. `GetDepotIndex` uses map `m2` only on real depot tiles; portal housings currently set it to0 without declaring a depot identity. That0 is **not** a usable DepotID.
- Every rail portal's upper housing already has physical magazine behavior. Group7B proves ordinary traffic can pass beside its fully stored cutter. `GetLayerPortalMagazineExit`, `GetLayerPortalAdmittedTrackdirs`, `CheckTrainStayInMagazine` and `IsLayerPortalMagazineBusy` currently admit the pair's own controller/hauler only. Another destination requires explicit admission and real entry/exit; a saved ID alone cannot establish arrival.
- `GetTBMCutterSteeringTarget` currently yields to all ordinary depot orders. `GetTBMExchangeBay` still names the true spoil exchange location. `TBMProject.portal`, geological commissioning anchor and Surface origin retain their existing meanings. Changing the selected hangar must not rewrite any of these.

## Implementation direction

Keep ordinary native depot orders and their existing synchronization/save representation. Give a selectable portal magazine a **real Depot pool object** backed by its existing physical storage, allocated by the synchronized command after full admission. Reuse that stable object for subsequent orders; never add a parallel portal registry or fabricate an ID from tile bits. Ordinary rail depots keep their existing identities. Lazy registration avoids requiring spare depot-pool capacity merely to load an older world with existing portals.

The implementation stores an actual native DepotID in portal `m2`, with explicit `m4` bit0 presence. Both existing constructors initialize `m4` to0; no older save needs depot allocation. `SaveLoadVersion::TBMHangarDepots` is397. Native map/depot accessors recognize the registered storage, native naming uses layer/coordinates without requiring a nearby town, portal demolition destroys the real Depot before removing its physical marker, and full-load validation checks the map/pool identities in both directions. Actual397 return/parked files now load and continue successfully. Malformed/preview acceptance remains pending. **Current executables write397.** Preserve every395/396 input and do not rerun historical writers that hard-code396.

Native ordinary depot storage retains its existing capacity. A portal magazine admits one cutter plus its own assigned exchange hauler during work settlement; another stored cutter is a full destination and unrelated moving traffic must clear. Existing physical magazine storage needs no new excavation charge. Any additional bay beyond that capacity would need a real paid footprint and remains outside this first destination contract. Whole stored trains may coexist with public through traffic under the verified Group7B rule; moving/partly stored trains retain the ordinary safety guards.

An ordinary explicit return/halt order must first interrupt new cutting and preserve partial work, then settle the cutter's existing loaded spoil at its real exchange bay before the empty consist travels to the chosen hangar. The native order remains the sole selected travel destination; do not introduce a private order queue or redefine the geological anchor as a destination. Service visits must retain Group4's native service behavior and physical cargo custody. Before implementing phase arbitration, read the order completion path in `VehicleEnterDepot`/`ProcessOrders` so a native arrival cannot erase the needed intent prematurely. Resume must use the same accepted work from the actual parked location.
